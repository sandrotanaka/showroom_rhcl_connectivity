= A aplicação e a proposta
:navtitle: A aplicação

*Leitura: 8 minutos.* Não há comando aqui — é o mapa que faz o resto do dia ter
sentido.

== A proposta em uma frase

Pegar uma aplicação que já está em produção e, **sem alterar uma linha do código
dela**, dar-lhe procedência, identidade e valor comercial.

image::camadas.svg[Cada trilha acrescenta uma camada à mesma aplicação,align="center"]

Cada trilha responde a uma pergunta diferente sobre **os mesmos seis pods**. É
por isso que a ordem importa e que nenhuma delas é opcional para a tese: sozinha,
cada uma parece "mais uma ferramenta"; juntas, são o que se chama de plataforma.

== Por que o bookinfo

É a amostra canônica do Istio — provavelmente você já a viu. Ela vem do projeto
Istio, mantida em
https://istio.io/latest/docs/examples/bookinfo/[istio.io/docs/examples/bookinfo,window=_blank],
e é usada aqui **como o upstream a publica**: mesmos serviços, mesmas três
versões do `reviews`, mesmos manifestos de aplicação.

[NOTE]
.O que é do upstream e o que é nosso
====
A aplicação é do projeto Istio (_Istio Authors_, Apache 2.0). Nada do código
dela foi alterado — e essa é a condição do exercício, não uma economia: a tese
do dia é que procedência, identidade e valor comercial se acrescentam **por
fora**.

O que este workshop acrescenta são as camadas: as policies do Service Mesh, as
do Connectivity Link, o pipeline e o catálogo. Elas não existem no upstream.

Se quiser comparar exercício a exercício, a
https://istio.io/latest/docs/tasks/[lista de tasks do Istio,window=_blank] cobre
o mesmo terreno da trilha 2 sem nada de OpenShift em volta.
====

Escolhemos por três motivos práticos:

[cols="1,3"]
|===
| *Três versões de um serviço* | o `reviews` tem v1, v2 e v3 **no ar ao mesmo tempo**. Canário só se distingue de troca de versão quando existe uma terceira versão saudável recebendo zero por cento.
| *Prova visível* | recarregar a página muda as estrelas. Dá para verificar um exercício sem abrir terminal.
| *Quatro linguagens* | Python, Ruby, Java e Node — o upstream chama a aplicação de _polyglot_, e é de propósito. Tudo o que a plataforma entrega vale para as quatro igualmente — e é isso que separa "propriedade do caminho" de "biblioteca da aplicação".
|===

== Os quatro serviços

[cols="1,1,3"]
|===
| Serviço | Linguagem | O que faz

| `productpage` | Python | a UI. É o único que o navegador vê, e o único que chama outros dois.
| `details` | Ruby | metadados do livro. Não chama ninguém.
| `reviews` | Java | as resenhas. *v1 não chama o `ratings` e não mostra estrelas; v2 chama e mostra estrelas pretas; v3 chama e mostra estrelas vermelhas.* É o único que chama o `ratings`.
| `ratings` | Node | as notas. Ponta da cadeia.
|===

== A mesma aplicação, três vezes

A documentação do Istio explica o bookinfo com **dois** desenhos, e a escolha é
deliberada: a diferença entre eles é o argumento. Vamos usar os dois, e
acrescentar um terceiro.

.Sem Service Mesh — o que o time de aplicação escreveu
image::istio-noistio.svg[O bookinfo sem Istio: quatro serviços chamando uns aos outros diretamente,align="center",width="640"]

Quatro serviços, quatro linguagens, chamadas HTTP diretas. Não há mTLS, não há
métrica por serviço, não há trace. Se você quiser qualquer uma dessas três
coisas aqui, alguém abre um editor de código.

.Com Service Mesh — o mesmo código, com um contêiner a mais em cada pod
image::istio-withistio.svg[O mesmo bookinfo com sidecars Envoy injetados em cada pod,align="center",width="640"]

Compare os dois desenhos: **os quadrados são os mesmos**. O que apareceu foi um
Envoy ao lado de cada serviço, e um na borda. Nenhuma linha das quatro
aplicações mudou — e, a partir daí, mTLS, métrica e trace existem para as
quatro igualmente.

É essa a frase que o dia inteiro persegue, e ela começa aqui.

.Neste cluster — onde o desenho do upstream deixa de valer
image::topologia.svg[Topologia do bookinfo neste ambiente,align="center"]

O terceiro é nosso, e existe porque a borda é diferente. Onde o upstream desenha
um *Ingress Envoy* do Istio, aqui há um `Gateway` da Gateway API publicado por
uma `Route` do OpenShift — e, na trilha 3, um segundo gateway com policies de
produto. O miolo continua idêntico ao desenho 2.

[NOTE]
.Sobre os dois primeiros desenhos
====
Eles são do projeto Istio (_Istio Authors_, Apache 2.0), reproduzidos sem
alteração de
https://istio.io/latest/docs/examples/bookinfo/[istio.io/docs/examples/bookinfo,window=_blank].
Os rótulos estão em inglês porque são nomes de serviço e de produto — que, por
regra deste material, não se traduzem.
====

Três coisas para reparar no terceiro desenho, porque as três voltam como exercício:

**O gateway não é da aplicação.** Ele é um Envoy na borda, e é onde a trilha 3
decide quem entra e quanto passa. A aplicação não sabe que ele existe.

**Todo pod tem um segundo contêiner.** O *sidecar* foi injetado pelo Service
Mesh, não declarado pelo time de aplicação. É ele que faz mTLS, produz métrica e
emite trace — sem uma linha de instrumentação nos quatro serviços.

**As setas são a topologia real, não a desenhada.** Hoje só o `productpage`
chama `details` e `reviews`, e só o `reviews` chama `ratings` — mas isso é
verdade **por acidente**: é o que o código faz. O módulo 2.2 transforma isso em
declaração, e você vai ver um vizinho do mesmo namespace ser recusado.

== A dinâmica de uma requisição

Uma chamada a `/productpage` percorre isto:

[source]
----
navegador
  └─ gateway (Envoy)            <1>
       └─ productpage           <2>
            ├─ details          <3>
            └─ reviews (v1|v2|v3)   <4>
                 └─ ratings     <5>
----
<1> decide *quem entra*: chave de API, plano comercial, limite. Duas chamadas
    fora do processo — autorização e rate limit — que aparecem no trace com
    tempo medido.
<2> a única resposta que o navegador enxerga; monta a página com o que os outros
    devolverem.
<3> sai em paralelo com o próximo. Se falhar, o `productpage` ainda responde.
<4> a decisão de qual versão recebe a chamada não está no código nem no deploy:
    está num peso, fora dos dois.
<5> ponta da cadeia. É a ele que o módulo 2.5 injeta falha, para ver a página
    degradar sem quebrar.

[NOTE]
====
O `reviews` degrada com elegância: se o `ratings` cair, a página carrega sem as
notas. O `productpage` **não** degrada se o `reviews` cair. Essa assimetria não
está escrita em documento nenhum da aplicação — você a descobre no módulo 2.5,
injetando falha.
====

== O que cada trilha acrescenta

*Trilha 1 — de onde isto veio?* Hoje as seis imagens vêm de um registry de
terceiro, sem varredura e sem assinatura: exatamente o que a maioria das
organizações põe em produção sem pensar. A trilha dá **procedência** — manifesto
validado, imagem espelhada, assinada e registrada num log de transparência.

*Trilha 2 — quem fala com quem aqui dentro?* A chave de API abre a porta da rua;
não abre o cofre. A trilha instala identidade entre serviços, observabilidade sem
instrumentação, e as ferramentas para responder *o que acontece quando quebra*.

*Trilha 3 — quem entra, quanto pode, quanto vale?* A borda muda de dono: a mesma
aplicação passa a ter duas fronteiras no mesmo hostname — UI pública, API sob
chave — e três planos comerciais com cota e métrica.

== O fecho

Ao final do dia, este comando é a prova:

[source,role="execute"]
----
oc get deploy -n bookinfo -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.template.spec.containers[0].image}{"\n"}{end}'
----

As imagens são as mesmas do começo — só a **origem** mudou, e isso foi assunto da
trilha 1. Nada do que você vai construir hoje pediu alteração no código dos
quatro serviços.
