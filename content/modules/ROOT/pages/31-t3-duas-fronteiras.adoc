= 3.2 Duas fronteiras, um hostname
:navtitle: 3.2 Duas fronteiras

*Tempo: 20 minutos*

[NOTE]
.Quem executa este módulo
====
*`plat-eng`* — engenharia de plataforma. A credencial e os links estão em
xref:03-acessos.adoc[Acessos]; é a mesma para OpenShift, GitLab e Developer Hub.

Um parceiro não conseguiria — e dá para conferir **sem trocar de usuário**:

[source,role="execute"]
----
oc auth can-i create authpolicies -n bookinfo --as=plat-eng
oc auth can-i create authpolicies -n bookinfo --as=acme-trips
----

`yes` e `no`. A permissão vem da função, não da pessoa.
====

A UI responde `401`. A pergunta que isso levanta é melhor do que o erro: **por
que uma rota sem policy nenhuma é negada?**

== Objetivos

* Explicar o efeito de uma policy de escopo de gateway sobre rotas novas.
* Tornar uma rota pública com uma policy, e não com a ausência de uma.
* Colocar UI e API sob fronteiras diferentes no mesmo hostname.

== Exercício 1: quem está negando

. Procure a policy que mira o gateway:
+
[source,role="execute"]
----
oc get authpolicy -n ingress-gateway
oc get authpolicy prod-web-deny-all -n ingress-gateway -o jsonpath='{.spec.rules}' | python3 -m json.tool
----

O `prod-web` carrega uma `AuthPolicy` que **nega tudo**. Ela vale para toda rota
anexada que não declare a sua própria — e a sua rota nova não declarou.

[IMPORTANT]
====
Este é o padrão que separa uma plataforma de um gateway com regras: o default é
*negar*, e cada rota precisa declarar explicitamente o que aceita. Uma rota
esquecida não fica aberta — fica fora do ar, o que é ruidoso e, portanto, seguro.
====

== Exercício 2: público é uma decisão, não um esquecimento

A UI é para qualquer pessoa. Isso **não** significa "sem policy": significa uma
policy que permite anônimo.

. Declare:
+
[source,role="execute"]
----
oc apply -f - <<'YAML'
apiVersion: kuadrant.io/v1
kind: AuthPolicy
metadata:
  name: bookinfo-ui-authpolicy
  namespace: bookinfo
spec:
  targetRef:
    group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: bookinfo-ui
  rules:
    authentication:
      anonimo:
        anonymous: {}
YAML
----

. Confirme:
+
[source,role="execute"]
----
D=$(oc get ingresses.config/cluster -o jsonpath='{.spec.domain}')
curl -sk -o /dev/null -w 'UI -> %{http_code}\n' "https://bookinfo.$D/productpage"
----

. Você deve ver `200`.

. Uma rota anônima ainda precisa de proteção de capacidade — senão qualquer um
  esgota a aplicação:
+
[source,role="execute"]
----
oc apply -f ~/rhcl/samples/bookinfo/rhcl/24-ratelimitpolicy-ui.yaml
----

== Exercício 3: a API, sob chave

. Aplique a policy da rota de API e as chaves:
+
[source,role="execute"]
----
oc apply -f ~/rhcl/samples/bookinfo/rhcl/22-authpolicy.yaml
oc apply -f ~/rhcl/samples/bookinfo/rhcl/26-identity-apikeys.yaml
----

. Sem chave:
+
[source,role="execute"]
----
D=$(oc get ingresses.config/cluster -o jsonpath='{.spec.domain}')
curl -sk -o /dev/null -w 'API sem chave -> %{http_code}\n' "https://bookinfo.$D/api/v1/products"
----

. Com chave:
+
[source,role="execute"]
----
KEY=$(oc get secret -n kuadrant-system -l app=partner,devportal.kuadrant.io/apiproduct=bookinfo-api \
  -o jsonpath='{.items[0].data.api_key}' | base64 -d)
curl -sk -o /dev/null -w 'API com chave -> %{http_code}\n' "https://bookinfo.$D/api/v1/products?APIKEY=$KEY"
----

. Agora tente a mesma chave contra a UI, e depois uma chave de **outro** produto
  contra esta API. O selector da `AuthPolicy` exige o label
  `devportal.kuadrant.io/apiproduct` — **assinatura é por produto, não por
  gateway**.

bash ~/workshop/scripts/workshop.sh verifica 32

.Se falhar
[%collapsible]
====
Antes de improvisar, peca o diagnostico — ele olha as camadas de baixo e
imprime sintoma, causa provável e comando:

[source,role="execute"]
----
bash ~/workshop/scripts/workshop.sh diagnostica 32
----

*A UI continua em `401` depois da policy anônima?* Confira se ela foi aceita e
está valendo:

[source,role="execute"]
----
oc get authpolicy bookinfo-ui-authpolicy -n bookinfo \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status} ({.message}){"\n"}{end}'
----

*A chave existe mas dá `401`?* O Authorino nem sempre reindexa o Secret depois de
uma troca de policy. Toque a chave para forçar:

[source,role="execute"]
----
oc annotate secret -n kuadrant-system -l app=partner reindex="$(date +%s)" --overwrite
----
====

== O que isso significa

O mesmo hostname passou a ter **duas fronteiras**, decididas por rota: `/` é
pública e limitada; `/api/v1` exige chave e é ligada a um produto.

Essa é a fronteira do **produto**, e não do endereço — e é exatamente o que um
gateway com regras por host não consegue expressar sem duplicar hostname,
certificado e configuração.
